# API Integration Tests

Playwright + TypeScript framework for API integration testing.

- **Compare mode** (during migration): the same request goes to V1 and V2, and the cleaned responses must match.
- **Regression mode** (after migration): V2 only, checked against status, field values, schemas and saved baselines.

Both modes use the same endpoint definitions and test data. No browsers are used, so `npx playwright install` is never needed.

## Quick start

```bash
npm ci
cp env/.env.example env/.env.dev        # fill in the URLs (and auth values if needed)
npx playwright test projects/prj-a/api-crew --project=comparison
```

## Structure

```
projects/                     written by testers
  prj-a/
    project.config.ts         where each API lives (env variable names), auth, shared ignore rules
    api-crew/
      endpoints/              how to call and compare each endpoint (+ index.ts listing them)
      testdata/               what to send and what to expect, one JSON per endpoint
      schemas/                optional: expected response structure, one per endpoint
      tests/                  api-crew.compare.spec.ts, api-crew.regression.spec.ts
baselines/<env>/<project>/<api>/<endpoint>/<case>.json     generated by the framework, committed
reports/<project>/<api or all-apis>/html + junit           generated per run, not in git
src/                          the framework engine, same for every project
  suites/                     comparisonSuite.ts, regressionSuite.ts: the test logic, written once
  http/                       apiClient.ts (sends requests), auth.ts (tokens)
  compare/                    normalize.ts (clean payloads), diff.ts (find differences)
  data/                       loadTestCases.ts, baselineStore.ts, validateSchema.ts
  config/                     env.ts (environment variables), projectConfig.ts (project.config.ts, folders)
  fixtures.ts                 the only fixture: a pool of clients, one per project, API and version
  types.ts                    the contract between projects and the framework
  selfcheck/                  unit tests of the framework and consistency checks of all projects
pipelines/                    pr-validation.yml, api-tests.yml
env/                          .env.<environment> files (only .env.example is in git)
```

Rules that keep it consistent:

- **Folder names are the source of truth.** Project and API names come from `projects/<project>/<api>/`.
- **File names connect the pieces.** `endpoints/validLicenses.ts` uses `testdata/validLicenses.json` and, if present,
  `schemas/validLicenses.schema.json`. The export name in `endpoints/index.ts` must equal the file name.
- **Testers write only in `projects/`.** The framework writes only to `baselines/` and `reports/`.

## How a test runs

1. `tests/api-crew.compare.spec.ts` passes the api-crew endpoints to `comparisonSuite.ts`.
2. The suite works out project and API from the folder, loads each endpoint's test data, and creates one test per case.
3. `fixtures.ts` gives the test a V1 and a V2 client for api-crew, using `project.config.ts` and `env/`.
4. `apiClient.ts` sends the same request to both (with auth from `auth.ts`).
5. `normalize.ts` removes ignored fields and sorts unordered lists; `diff.ts` finds every difference.
6. Status, `expectFields` and the optional schema are checked; the report shows both responses and the differences.
7. In record mode, a matching result is saved as a baseline.

Regression follows the same path with `regressionSuite.ts`, calling only V2.

## Writing an endpoint

`endpoints/validLicenses.ts`:

```ts
export default defineEndpoint({
  method: 'GET',
  path: { v1: '/api/crew/{crewId}/licenses/valid', v2: '/api/v2/crew/{crewId}/licenses/valid' },
  ignore: ['meta.requestId', '**.lastUpdated'],     // allowed to differ
  sortArrays: { licenses: 'licenseNumber' },          // order does not matter
  // dropNulls: true,                                 // null and missing are the same
});
```

Then add it to `endpoints/index.ts`: `export { default as validLicenses } from './validLicenses';`

Ignore syntax: `meta.requestId` exact path, `licenses[].id` a field in every list item, `**.lastUpdated` any depth,
`*` any single field. Sort syntax: field to sort by, `*` for lists of plain values, `$` for a root list.

## Writing test data

`testdata/validLicenses.json` is a list of cases:

| Field | Meaning |
|---|---|
| `id`, `description` | Required. `id` is unique per file and names the baseline file. |
| `pathParams`, `query`, `body`, `headers` | What to send |
| `expectedStatus` | Expected HTTP status |
| `expectFields` | Values the V2 response must contain, e.g. `{ "licenses[0].status": "VALID" }` |
| `tags` | e.g. `["smoke"]`, run with `--grep @smoke` |
| `skipComparison` | Reason text; skips the case in compare mode (intended V2 change) |

Unknown fields are rejected with a clear message, so a typo never silently disables a check.

## Project configuration

`projects/prj-a/project.config.ts` holds **names** of environment variables, never values:

```ts
export default defineProject({
  defaults: {
    v1: { urlEnv: 'PRJA_V1_URL', auth: { type: 'azureAd', scopeEnv: 'PRJA_V1_SCOPE' } },
    v2: { urlEnv: 'PRJA_V2_URL', auth: { type: 'azureAd', scopeEnv: 'PRJA_V2_SCOPE' } },
  },
  apis: {
    'api-crew': {},                                   // uses defaults
    'api-b': { v2: { urlEnv: 'PRJA_B_V2_URL' } },     // own V2 host
  },
  rules: { ignore: ['**.traceId'] },
});
```

Auth types: `none`, `bearer` (`tokenEnv`), `apiKey` (`header`, `keyEnv`),
`azureAd` (`scopeEnv`, uses `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` unless overridden).
Base URLs are scheme and host (plus an optional base path); endpoint paths are appended.

## Running

| What | Command |
|---|---|
| One API, compare | `npx playwright test projects/prj-a/api-crew --project=comparison` |
| Whole project, regression | `npx playwright test projects/prj-a --project=regression` |
| Only smoke cases | add `--grep @smoke` |
| Another environment | `TEST_ENV=test npx playwright test ...` (uses `env/.env.test`) |
| Record baselines | `npm run record:baselines -- projects/prj-a` |
| Framework checks | `npm run test:selfcheck`, `npm run typecheck`, `npm run lint` |

Reports: `reports/<project>/<api>/html/index.html` (or `all-apis/`). Open with `npx playwright show-report <folder>`.

## From compare to regression

1. Run compare mode and get V1 and V2 to match (fix V2, or adjust ignore rules for legitimate differences).
2. Record baselines per environment and commit `baselines/`. Only cases where V1 and V2 matched are saved.
3. Regression checks V2 against expected status, `expectFields`, schema and baseline.
4. When V1 is retired: remove the V1 variables, the `*.compare.spec.ts` files and the `comparison` project in
   `playwright.config.ts`, and the `v1` entries in configs and endpoints.

Baselines suit stable test data. For data that changes over time, delete the baseline and rely on
`expectedStatus`, `expectFields` and a schema.

## Adding an API or a project

**New API in prj-a:** copy `api-crew/` to `api-<name>/`, rename the two spec files, replace endpoints, test data
and schemas, and add `'api-<name>': {}` under `apis` in `project.config.ts`. Nothing in `src/` changes.

**New project:** create `projects/prj-b/` with a `project.config.ts` and API folders as above.

`npm run test:selfcheck` tells you if anything is missing or inconsistent.

## Production-readiness guardrails

This repository is suitable for enterprise migration validation, but it must be treated as a governed release-quality asset rather than a casual developer playground.

The following protections are recommended before using it as an organization-standard test harness:

- Configuration validation must be explicit and early.
  - Every project/API must declare all required env vars and auth settings in `project.config.ts`.
  - CI should fail fast if a required URL or auth variable is missing before tests begin.
  - Missing or malformed config should be treated as a release blocker, not a recoverable runtime annoyance.

- Baselines must be reviewed and versioned as controlled artifacts.
  - `baselines/` should only be updated through a reviewed change, usually after a migration decision has been signed off.
  - Recording a baseline in an uncontrolled local session is acceptable for local exploration, but not for shared or production validation.
  - The recorded baseline should reflect the approved contract, not simply the current output of a draft implementation.

- Secrets and credentials must never be committed.
  - Keep all sensitive inputs in `env/.env.*` files only locally or in secure pipeline variable groups.
  - Do not store real tokens, client secrets, or tenant details in source-controlled files or issue comments.
  - The project config should reference env names only; actual values belong in secure secret storage.

- Validation must be narrow and evidence-based.
  - Compare mode is for migration investigation and should be used while V1 and V2 are both live.
  - Regression mode is for post-migration safety checks and should rely on approved baselines, schema validation, and explicit `expectFields` assertions.
  - Any skipped comparison case must be a conscious business decision with a recorded reason, not an accidental omission.

- Test data must be treated as contract documentation.
  - Every case should have a unique, meaningful `id`.
  - Unknown fields in data files should fail loudly, because silent drift is dangerous in a regulated environment.
  - A test case should be reviewable by a domain owner, not only by a developer who wrote the code.

- Operational discipline matters.
  - Run compare tests in isolated environments and with explicit filters.
  - Keep `@smoke` and other tag-based subsets for fast validation, while reserve broad runs for controlled pre-release checks.
  - Logs, responses and diffs should be treated as operational evidence; do not leave noisy or unreviewed output in shared run artifacts.

- CI/CD should protect the critical path.
  - `pr-validation.yml` should remain a non-invasive lint/type/selfcheck gate.
  - Live API execution should run only in controlled environments with approval and with secret management enabled.
  - For organization use, require reviewer sign-off for changes affecting framework files under `/src` and shared rules under `projects/`.

- The framework should evolve under change control.
  - Modifications to comparison logic, normalization rules, or auth handling should be treated as platform changes.
  - Any change that affects the meaning of a contract assertion should be reviewed as a policy change, not a routine fix.

This repo is operating at the level of an internal migration assurance platform. That is a strength, but it also means the codebase must be handled with the same discipline expected of a real organization project: reviewed changes, controlled secrets, explicit evidence, and clear ownership.

## CI (Azure DevOps)

- `pipelines/pr-validation.yml`: typecheck, lint and selfcheck on every pull request (no API calls).
  Add it as Build Validation on `main`, and require reviewers for changes under `/src`.
- `pipelines/api-tests.yml`: parameters environment, mode, scope and filter. Needs a variable group
  `api-tests-<environment>` with the variables named in the project configs. Use a self hosted agent
  if the APIs are internal.

## Troubleshooting

| Message | Meaning |
|---|---|
| `Environment variable X is not set` | Add X to `env/.env.<env>` or the variable group. Only that API fails. |
| `API "x" is not listed under "apis"` | Add it to `project.config.ts`. |
| `Problems in .../testdata/x.json` | The message lists each broken case; only that endpoint fails. |
| `N difference(s) between V1 and V2` | Real difference, or a field to add to `ignore` / `sortArrays` / `dropNulls`. |
| `Test case has no pathParams.x` | The endpoint path has `{x}` but the case does not provide it. |
